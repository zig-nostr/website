# deed: the nostr command line

**deed** is a command line for nostr, built on `zig-nostr`. It makes keys, builds and signs events, reads and writes NIP-19 codes, encrypts and decrypts with NIP-44, checks signatures, asks relays for events and publishes to them, syncs with NIP-77, sends private messages, runs a NIP-46 signer, talks to Blossom servers and NIP-98 HTTP endpoints, and keeps what it fetches in a local store that later runs can read without a network. One binary of under 3 MB for macOS, Linux and Windows, Intel and ARM, statically linked on Linux.

A deed is two things at once: a signed instrument, and a thing done. So is a nostr event.

## Install

macOS and Linux:

```sh
curl -fsSL https://raw.githubusercontent.com/zig-nostr/deed/main/scripts/install.sh | bash
```

Windows, in PowerShell:

```powershell
irm https://raw.githubusercontent.com/zig-nostr/deed/main/scripts/install.ps1 | iex
```

Each checks the download against the SHA-256 published beside it, and if the digest does not match it installs nothing and says so. On macOS and Linux deed goes into `~/.local/bin`. On Windows it goes into `%LOCALAPPDATA%\deed`, which is added to your `PATH`, so `deed version` works in a new terminal. Neither needs root or administrator rights.

`--version <tag>` installs a particular release and `--prefix <dir>` puts it somewhere else; on Windows they are `-Version` and `-Prefix` when the script runs as a file, and `$env:DEED_VERSION` and `$env:DEED_PREFIX` for the piped line. Windows on ARM gets the x86_64 build, which Windows 11 runs under emulation. The Windows binary is not code-signed, so Windows may show a warning the first time it runs.

## What it does

deed reaches relays and keeps what it finds. Every verb that does not need a socket works without one, so what comes out can be read before any of it leaves the machine. `deed help <command>` explains any of them.

| Verb | |
| --- | --- |
| `req` | build a subscription from flags or JSON, and run it: search, any tag, pagination, ids only |
| `fetch` | get the events a code names |
| `event` | build an event and sign it, and optionally publish it. Tag shortcuts, `@file` content and proof of work (NIP-13) |
| `publish` | offer signed events to relays, and print the ones they accepted |
| `post` | publish a note, a reply (NIP-10) or a comment (NIP-22) |
| `profile` | show a profile, or change your own while keeping every field you did not name |
| `count` | count the events that match a filter (NIP-45), or count a local store |
| `filter` | keep the events on stdin that match a filter |
| `kind` | look up an event kind by number or name |
| `key` | make a key, derive the public one, protect it as an ncryptsec (NIP-49), check keys, work with BIP-39 mnemonics (NIP-06) |
| `encode` | build a NIP-19 code out of its parts |
| `decode` | turn a NIP-19 code, or a NIP-05 identifier, into the fields it carries |
| `verify` | check that events are correctly signed |
| `encrypt` | encrypt a message to someone, with NIP-44, or with legacy NIP-04 under `--nip04` |
| `decrypt` | decrypt a NIP-44 or NIP-04 payload from someone |
| `gift` | wrap and unwrap events as NIP-59 gift wraps, and build NIP-17 private messages |
| `relay` | fetch relays' NIP-11 information documents |
| `relays` | show the relays a person reads from and writes to (NIP-65) |
| `bunker` | run a NIP-46 remote signer |
| `sync` | copy what is missing between relays, or between a relay and a store, with NIP-77 |
| `store` | inspect, export, import and trim a local event store |
| `curl` | run curl with a NIP-98 signed Authorization header |
| `admin` | manage a relay with the NIP-86 management API |
| `blossom` | list, upload, download, delete, check and mirror blobs on a Blossom server |
| `serve` | a local relay |
| `version` | print the version |

## A local relay

`deed serve` runs a relay on this machine, for development and tests. It listens on 127.0.0.1 port 10547 by default and prints its URL on standard output once it is listening, so a script can read it. Connections and errors go to standard error, and the relay runs until it gets SIGINT or SIGTERM.

```sh
deed serve                                          # 127.0.0.1:10547, events in a temporary store
deed serve --port 0 | head -1                       # let the system pick a port and print its URL
deed serve --store ~/.deed/relay --events seed.jsonl
deed serve --auth-required
```

`--hostname` sets the address to listen on, an IP address or `localhost`, and it defaults to 127.0.0.1. `--port` sets the port, which defaults to 10547, and 0 lets the system choose one. `--store` keeps events in a store at the path you give, and the store outlives the relay. Without it the events sit in a temporary store that is removed when the relay stops. `--events` loads a file of events before the relay starts, one JSON event per line. A bad line is reported on standard error and skipped. `--auth-required` sends a NIP-42 challenge on connect and answers nothing until the client has authenticated.

The relay speaks NIP-01, NIP-09 deletions, NIP-11 (the information document, served to HTTP requests that ask for `application/nostr+json`), NIP-40 expiration, NIP-42 AUTH, NIP-45 COUNT, NIP-70 protected events and NIP-77 negentropy. Every incoming event has its id and signature checked before it is stored, and a replaceable or addressable event keeps only the newest version. With `--store`, each accepted event is synced to disk before it is acknowledged.

Limits: a message is at most 512 KiB, a connection holds at most 64 subscriptions, a REQ carries at most 32 filters, a filter is answered with at most 10000 stored events, and a client that stops reading is disconnected once 4 MiB are waiting for it.

## The verbs compose

Each verb takes its inputs as arguments and, given none, reads them as newline-delimited records on standard input, writing one result per line:

```sh
export NOSTR_SECRET_KEY=$(deed key generate)

deed event -c "hello" | deed verify
cat drafts.jsonl | deed event - | deed publish wss://relay.example > sent.jsonl
```

`publish` prints each event a relay accepted, once the relays have answered or the deadline has passed, so what it writes out is what was published. Every relay's answer goes to standard error with the event's id on it, and the exit code is 0 only when every event was accepted by at least one relay.

## It keeps what it fetches

```sh
deed req -k 1 -l 50 --store ~/.deed/db wss://relay.example   # once, over the network
deed req -k 1 -l 50 --store ~/.deed/db --local               # again, dialling nothing
```

The second command opens no socket, and the events it prints are the same events: what is stored is what was signed, so they still verify. Every event is checked before it is stored or printed, so a relay cannot put a forgery, or an event nobody asked for, into the store or the output.

A store is one file. `--store` creates it the first time, and the directories above it as `mkdir -p` would, and a leading `~` is your home directory even when it was quoted. `--local` only reads, so it opens a store that already exists and says "there is no store at" a path that has none, rather than leaving an empty one behind. When a store will not open, the message says why: a directory in the way, no permission, a read-only file system, a full disk, or a file that is not a store. On Windows the file takes 1 GiB of disk from the first run, because LMDB sizes it to its whole map up front there; on macOS and Linux it grows with what is kept.

NIP-19 codes are read the way a QR code carries them: `deed decode NPUB1...` and `NOSTR:NPUB1...` work as the lowercase forms do, and a code that mixes cases is refused.

## Authentication

Keys come from `--sec` or from `$NOSTR_SECRET_KEY`. A key on a command line lands in your shell history and in the process table, so the variable is the better habit. Wherever a verb reads a secret key it takes `nsec1...`, 64 hex characters or an `ncryptsec1...`. An ncryptsec asks for its password on the terminal with echo off, or reads it from `$NOSTR_PASSWORD`; a password is never taken from an argument.

```sh
deed key encrypt "$NOSTR_SECRET_KEY" > me.ncryptsec   # asks for a password
deed key mnemonic                                      # a BIP-39 phrase
deed key from-mnemonic --public                        # the npub at m/44'/1237'/0'/0/0
```

A relay that keeps some events behind authentication (NIP-42) is answered with `--auth` on `req`, `fetch` and `publish`. Without it deed signs nothing it was not asked to sign. `--force-pre-auth` waits for the challenge and answers it before asking anything.

```sh
deed req --auth -k 4 -p npub1... wss://relay.example
```

## Finding a person's relays

deed has no built-in relay list and contacts only the relays you name. `deed relays` reads a person's relay list (kind 10002, NIP-65), checks its signature, and prints where they read and where they write. `DEED_RELAYS` names the relays to ask on every run, and `--relay` adds to it. With no relay list published, the relay hints in their kind 3 follow list are used instead.

```sh
export DEED_RELAYS=wss://purplepag.es
deed relays npub1...                 # url, a tab, then read, write or read,write
deed relays --outbox npub1...        # where they publish: read their notes there
deed relays --store ~/.deed/db npub1...   # use a cached list first, and keep what is fetched
deed req -k 1 -l 20 -a npub1... $(deed relays --outbox npub1...)
```

`fetch` and `post` do not follow a person to their own relays by themselves. Find the relays with `deed relays` and name them.

## Syncing

`deed sync` copies what one side lacks, using NIP-77 negentropy so that only ids cross the wire to find the difference. A relay that does not support it is named on standard error and asked with a plain REQ instead, which downloads what the filter matches.

```sh
deed sync -k 1 -a npub1... wss://from.example wss://to.example      # relay to relay
deed sync -k 1 -a npub1... wss://relay.example --store ~/.deed/db   # pull into the store
deed sync -k 1 -a npub1... --store ~/.deed/db wss://relay.example   # push from the store
```

Each event that lands is printed as a line of JSON. `--quiet` prints one line of counts instead.

## The local store

`deed store` works on a store that already exists, and only `import` creates one:

```sh
deed store stats  --store ~/.deed/db            # counts per kind, oldest and newest, size on disk
deed store export --store ~/.deed/db -k 1 -l 100   # matching events, newest first, one per line
deed store import --store ~/.deed/db < events.jsonl   # each event is verified first
deed store prune  --store ~/.deed/db --max 10000      # keep the newest 10000
deed store delete <id> --store ~/.deed/db             # remove one event
```

`prune` and `delete` remove events from the local file and nothing else. `count --local` and `profile --store` read the same store.

## Running a signer

`deed bunker` holds a key and signs for the clients it trusts (NIP-46), over the relays you give it. It prints a `bunker://` URI for a client to connect with, and `--qrcode` prints the same URI as a QR code on standard error.

```sh
deed bunker --qrcode wss://relay.example
deed bunker --persist ~/.config/deed/bunker.json wss://relay.example
deed bunker connect 'nostrconnect://...' wss://relay.example
```

Only authorized clients are served: those whose pubkey was given with `--authorized-keys`, and the one that presents the URI's secret. A secret is good for one client, and once it is used a new URI is printed. Nothing is asked interactively. With `--persist` the key, the relays and the authorized clients survive a restart, in a file only its owner may read; give it an ncryptsec to keep the key encrypted there.

## Private messages

`deed gift` wraps events as NIP-59 gift wraps and builds NIP-17 direct messages. It sends nothing itself: it prints wraps, one per line, for `deed publish`.

```sh
deed gift dm --to npub1... "see you at six" | deed publish wss://relay.example
deed req -k 1059 -p npub1... wss://relay.example | deed gift unwrap --json
```

`dm` adds a copy for you so your other clients can show the message. `unwrap` prints the rumor inside each wrap, and says which check failed (the wrap, the seal, the rumor or the sender) when one does. `encrypt` and `decrypt` take `--nip04` for older clients. NIP-04 has no authentication, so a successful decrypt proves nothing about who wrote the message, and it is there for interoperability only.

## HTTP verbs

Four verbs talk to a web server rather than a relay, each with a deadline and a cap on how much it will read.

```sh
deed relay wss://relay.example                               # the NIP-11 document, one JSON line per relay
deed decode bob@example.com                                  # NIP-05: the pubkey and relays the domain lists
deed curl -X PUT -d '{"a":1}' https://example.com/api/thing  # curl with a NIP-98 Authorization header
deed admin relay.example.com banpubkey npub1... "spam"       # a NIP-86 call to a relay
deed blossom upload photo.jpg -s cdn.example.com             # a blob, by its sha256
```

`curl` signs a kind 27235 event for the request and hands the rest to the system curl, whose exit status becomes its own. `admin` signs each call with your key and prints the relay's result. `blossom` has `list`, `upload`, `download`, `delete`, `check` and `mirror`: an upload is confirmed only when the server's sha256 and size match the file, and a download is written only when its sha256 matches.

## Judging what it fetches

deed's output is one verified event per line, which makes it a clean first stage for anything that classifies text. The [Jev example](https://github.com/zig-nostr/deed/tree/main/examples/jev) fetches the newest thousand notes from five relays, drops the app data some clients publish as notes, and has [Jev](https://docs.typesafe.ai), TypeSafe's classification model, answer three questions about each: what it is about, how much substance it carries, and whether it is spam. The thresholds that decide what to keep are plain constants in the script.

```sh
export TYPESAFE_API_KEY=...
examples/jev/rank-notes.sh 1000 > ranked.jsonl   # most substance first, spam dropped
```

On one run, 629 of 1,000 notes were text worth judging, 157 of those were dropped as spam, and the whole run cost about two cents. The example's README has the full numbers and what to watch for.

## How fast it is

A one-shot command runs in about 2.3 ms and under 2 MB of memory. deed signs and verifies about 31,000 events a second each, stores 100,000 events from a relay at about 17,000 a second, and answers a lookup from that store in about 3 ms, start to finish. The full numbers, and how to reproduce them, are on the [performance page](/performance#deed).
